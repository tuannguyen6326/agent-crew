# Per-harness verified facts

Read this before acting on a specific harness. Every fact traces to current Agent Crew code (the provenance in parentheses); nothing here is imported for an unsupported runtime.
Flag mapping shared by all: `--model` maps to claude `--model`, codex `-m` and opencode `-m`; effort maps to claude `--effort` and codex `-c model_reasoning_effort=<tier>` - codex has no effort FLAG, `-c` is its global config-override mechanism - and opencode ignores it (`bin/ac-spawn.sh` header + `bin/ac-backend.sh ac_build_launch`, the shared launch mote every mechanism composes its launch line with).

## claude

- Launch: `claude --permission-mode auto --session-id <uuid>`, adding `--model <name>` and `--effort <tier>` when set (`bin/ac-backend.sh ac_build_launch`; the `--session-id` is minted by the CALLER, so a crewmate pins one it can resume later - `bin/ac-spawn.sh build_launch` - and a one-shot pane turn pins none).
- Permission/trust dialogs: `--permission-mode auto` means routine per-tool permission prompts do not stall a crew launch; a genuine interactive prompt still surfaces as herdr `agent_status=blocked` (`bin/ac-backend.sh herdr_agent_blocked`).
- Effort tiers: `low|medium|high|xhigh|max`. `ultracode` is a preset, not a tier - the launch line gets `--effort xhigh` and, once the TUI is up, `/effort ultracode` is typed in as its own line; claude built-in only (`bin/ac-spawn.sh` effort handling + `deliver_kickoff`).
- Skill / slash invocation: type the slash command as its OWN submitted line - the kickoff path delivers `/effort ultracode` exactly this way (`bin/ac-spawn.sh deliver_kickoff` / `kickoff_acked`).
- Submit hazard: a positional prompt does NOT auto-submit in the interactive claude TUI, so the kickoff prompt is delivered as its own verified line, never as a launch argument (`bin/ac-spawn.sh` kickoff-prompt delivery).
- ONE-SHOT PANE ARM, mid-turn input: `claude -p` does NOT fold text written into its pane mid-turn into that turn, so a claude gate rung cannot DECLARE that it was steered. VERIFIED 2026-07-23 on claude 2.1.218 by the two-leg probe in the codex "mid-turn input" bullet below, run identically against `--harness claude`: 3 raw `herdr pane send-text` + `enter` writes were issued while `pgrep` proved `claude -p <prompt>` alive (pid 78342, argv the fleet's own one-shot form), and the final message came back byte-identical to the no-write leg - `{"verdict":"approve","mid_turn_input":""}` - while a write surfaced afterwards in the pane as `zsh: command not found: <token>`, i.e. it fell through to the SHELL rather than reaching the turn. NOT contradicted by `--input-format stream-json` ("realtime streaming input", `claude --help`): that is a different invocation, and the fleet's one-shot form (`bin/ac-pane-agent.sh oneshot_launch`) passes it nowhere. Whether that flag WOULD open a receiving surface is UNPROVEN and its discriminating test is one `claude -p --input-format stream-json` run fed on stdin mid-turn.
- Resume: SUPPORTED. `claude --resume <session_id>`; claude keys sessions by cwd, so a resume asks the pool for the old worktree slot back, is meant for same-stage revisions only, and rides `bin/ac-spawn.sh <new-id> <project> --resume-from <old-id>` (`bin/ac-backend.sh ac_build_launch` resume branch + `bin/ac-spawn.sh` header).
- Read-only inspection: `bin/ac-follow.sh <id>` streams the full transcript; `bin/ac-session.sh <id>` prints a forked (safe) resume, `--talk` an un-forked one that is refused mid-turn AND when the backend is unobservable - liveness unknown is treated like busy, not like safe-to-proceed (`bin/ac-follow.sh`, `bin/ac-session.sh` headers).
- Exit: when the pane process exits the window goes away and `bin/ac-crew-state.sh <id>` prints `gone`; when the backend itself cannot be read it prints `unobservable: ...` instead - never a death.
